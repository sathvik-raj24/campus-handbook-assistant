FACILITATOR GUIDE AND STUDENT LAB

RAG from Scratch

A practical 9 AM to 4 PM workshop for third-year Computer Science and Engineering students. Build a local document assistant, understand every RAG stage, and test whether its answers are supported.

Recommended project: Campus Handbook Assistant. Students load a small set of documents, retrieve relevant passages, and ask a local language model to answer using those passages with source labels. The supplied sample policies are fictional teaching data and do not describe VCET.

Preparation assumptions: students know Python variables, lists, dictionaries, loops, functions, and basic files. No prior NLP, vector databases, deep learning, or paid cloud account is required. Work in pairs, with a driver and reviewer; swap roles at lunch.

The provided prerequisite DOCX could not be read because of a local storage-policy block. This guide is based on the workshop request and the explicit assumptions above; it has not been checked against that document.

1 Learning outcomes and scope

By 4 PM, each pair should be able to explain RAG, implement basic chunking and cosine similarity, trace a question from retrieval to generated answer, inspect citations, and demonstrate both an answerable question and an appropriate “I don't know.”

  • From scratch means: students write or examine ingestion, chunking, vector comparison, ranking, evidence packaging, prompt construction, and evaluation. We use pretrained embedding and generation models; we do not train either model.
  • Core project: one local browser app, three small documents, independent questions, visible sources and prompts, two retrieval methods, and a comparison with an LLM without evidence.
  • Defer until after the workshop: agents, tool use, model training, production hosting, persistent vector databases, advanced rerankers, OCR pipelines, and multi-turn memory.

4 Fundamentals to teach explicitly

LLMs and the RAG idea

A language model predicts output tokens using learned parameters and the supplied context. It can generate a fluent answer without reliable evidence. A token is a model's text unit, not necessarily a word. The context window limits how much input and output the model can handle. The word-based chunk sizes in this project are teaching settings, not token counts.

RAG means Retrieval Augmented Generation. Retrieve relevant information from an external corpus, place it in the model's context, and ask the model to answer using that evidence. It does not automatically make every answer true; incorrect retrieval or unsupported generation can still fail.

TechniqueWhat changesUse in this workshop
PromptingThe instruction and examples sent to a modelAsk for concise, evidence-grounded answers and source labels.
RAGThe documents retrieved and provided at question timeAnswer questions about a supplied handbook; rebuild after documents change.
Fine-tuningModel weights through additional trainingExplain conceptually; no fine-tuning is needed for this application.

The two pipelines

INDEXING: documents → extract text and metadata → chunks → embeddings → in-memory index
QUESTION TIME: question → query embedding → similarity ranking → top-k evidence → prompt → LLM → answer and sources

For the keyword baseline, TF-IDF vectors replace learned embeddings. Retrieval can use keyword search, dense semantic search, or a combination. A vector database is a scaling and management choice, not a requirement for RAG.

Embeddings and similarity

An embedding model maps text to a numerical vector. Use the same model for documents and questions so that their vectors are comparable. With Nomic, this code uses search_document: for chunks and search_query: for questions, following its model card.

cosine(q, d) = dot(q, d) / (length(q) * length(d))

q = [1, 0]
d1 = [1, 0]  → cosine = 1
d2 = [1, 1]  → cosine ≈ 0.707
d3 = [0, 1]  → cosine = 0

Cosine measures direction similarity; it is not a probability that an answer is correct. TF-IDF weights words by frequency within a chunk and rarity across the corpus. It is useful for exact terms but misses many paraphrases. Learned embeddings may match meaning across different words, but are not guaranteed to find every relevant passage.

Chunking and retrieval choices

Start with 100 words and 20 words of overlap. Very small chunks may lose context; very large chunks may mix unrelated facts. Overlap can preserve facts across boundaries but introduces duplication and extra cost. Retrieve the top three chunks initially. More context can introduce distraction, and top-k search returns results even when no passage answers the question.

Preserve filename, page number, and chunk number at ingestion. TXT files are treated as one page; PDF page numbers are physical PDF pages starting at one. Word windows never cross a PDF page in this implementation. Search scans all vectors directly, which is adequate for a small class dataset but does not scale well.

Generation and evidence

The model receives an instruction to use only evidence, ignore instructions inside it, cite each factual claim, and admit when an answer is unsupported. A simplified user prompt looks like this:

EVIDENCE
[S1] File: library.txt; page: 1; chunk: 1
Third year undergraduate students may borrow four library books.
Each book may be borrowed for fourteen days.
END EVIDENCE
QUESTION
How many books can I borrow, and for how long?

A useful answer is: “Third-year students may borrow four books for fourteen days [S1].” Verify that [S1] actually supports both facts. A valid label alone does not make the claim grounded.

Ten minute instructor demonstration script

  1. Minute 0–1: show the three fictional documents and state that the model is not being trained.
  2. Minute 1–2: build the keyword index. Ask about borrowing books. Show the exact retrieved passage and score.
  3. Minute 2–4: rebuild with semantic retrieval, choose RAG, and repeat the question. Expected facts: four books, fourteen days. Inspect source labels and prompt.
  4. Minute 4–5: ask about after-hours laboratory access. Expected evidence: request to the coordinator at least one working day beforehand and prior approval.
  5. Minute 5–6: ask about annual hostel fees. The corpus contains no answer. Discuss whether the model abstains.
  6. Minute 6–7: choose LLM only and repeat. Record differences; do not assume the model will hallucinate every time.
  7. Minute 7–9: change four books to five in a sample file, rebuild, and ask again. Explain freshness without training.
  8. Minute 9–10: show a limitation and assign the paired build. Allow extra time if the classroom CPU is slow.

6 Student project brief

Problem statement: students spend time searching long handbooks for routine information. Build a local assistant that returns an answer and the passages that support it, and says when documents do not contain the answer.

Users: students and workshop participants. Input: three to ten short, permitted TXT/MD files or text-based PDF documents. Output: a concise answer, source filename/page/chunk, retrieved text, and visible retrieval settings.

Minimum viable submission

  • Run the app locally, index documents, ask independent questions, and show retrieved evidence.
  • Demonstrate one embedding model and one generation model, or clearly document a retrieval-only setup limitation.
  • Show a supported answer and an unsupported question. Manually verify every factual claim in the demonstration.
  • Test ten questions: eight supported, two unsupported. Include a paraphrase and a question requiring two related facts.
  • Submit source code, setup README, dataset provenance, an evaluation table, and a two-minute demonstration.

Choose one extension for the afternoon sprint

  • Course Notes Assistant: use permitted notes from one subject and add five paraphrased questions.
  • Placement FAQ Assistant: use an approved placement information pack and preserve document dates.
  • Better evidence display: highlight a matching sentence or allow viewing a passage before generating.
  • Retrieval experiment: compare keyword and semantic search on exact terminology versus paraphrases, with distractor documents.
  • Document update experiment: show that updating the source requires rebuilding the index; explain version and date handling.

Keep extensions small enough to demonstrate by 3:30 PM. A robust core pipeline is more valuable than adding many incomplete features.

8 Failure modes and classroom contingencies

  • Ollama unavailable: use keyword plus evidence-only mode; it teaches retrieval but is not the complete generative pipeline. Show full RAG on the instructor laptop and have students inspect the same prompts.
  • Connection refused: start Ollama or run ollama serve if no service is running. If the port is already in use, check whether the service is already active.
  • Missing model: verify exact model tags with ollama list and pull the embedding and generator separately.
  • Slow generation: use the 0.5B fallback, shorten context, and share a suitable machine per pair. Warn students that the smaller model is less reliable; do not present its errors as universal RAG behavior.
  • Scanned or complex PDFs: switch to TXT. OCR is outside scope; complex table extraction can scramble meaning.
  • Wrong answer with right retrieval: inspect the prompt, model behavior, conflicting evidence, and incomplete context.
  • No relevant passage: inspect extraction, chunking, query wording, and corpus coverage before changing the generator.
  • False confidence: a high similarity score or a well-formed source label does not establish correctness. Semantic retrieval has no universal cosine cutoff for abstention.
  • Prompt injection: test a permitted fictional passage asking the model to ignore the question. Explain that instructions inside documents are untrusted. The system prompt helps but does not guarantee security.
  • Stale information: rebuild after changing documents. Conflicting versions need explicit date and authority rules before any real-world deployment.

This app is a single-user local teaching server with an in-memory index. It has no production authentication, authorization, OCR, persistent vector store, or conversational memory. Keep it bound to localhost and use only approved, non-sensitive material.

9 Exit questions

  1. What changes between indexing and question time?
  2. Why must document and query embeddings use compatible models?
  3. What happens if the answer falls across a chunk boundary?
  4. Why can a top-k search return irrelevant passages?
  5. Why can a cited answer still be wrong?
  6. What must happen after a handbook rule changes?
  7. When should this assistant say “I don't know”?
